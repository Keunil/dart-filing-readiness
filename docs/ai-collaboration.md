# AI 활용 및 문제 해결 과정

작성 기준일: 2026-10-27. 사용 도구: Codex AI Coding Agent. 이 기록은 이번 과제 작업에서 확인한 문제와 설계·구현 결정을 정리한다. 사용자가 직접 내린 지시와 Agent가 제안한 구현 선택을 구분하며, 과거 구현을 이번의 신규 수정으로 쓰지 않는다.

## 1. 사용자 요청과 범위 결정

사용자는 최신 코드를 확인한 뒤 DART Filing Readiness 부분을 활용해 과제 요구사항에 맞는 제출물을 만들고, 별도 저장소와 적절한 배포 서비스를 판단해 준비하도록 요청했다. 해결하려는 문제는 공시 접수 전 수기 체크의 업무 집중과 오류다.

Codex는 과제 안내의 제출물 다섯 가지와 평가 비중을 추출했다. 기존 코드의 점검 엔진을 활용하고 독립 정적 앱을 만드는 방식을 제안했다. 배포 대상은 전체 업무 시스템이 아니라 파일 선택·체험·점검·근거 확인·결과 다운로드가 가능한 제출용 앱으로 정했다.

기존 소스 기준 커밋은 `0d4d1c6a2753c1c5e5499495dcd5fb67a152605e`다. 코드 재사용 범위와 변경 근거는 [provenance.md](provenance.md)에 남긴다. 기존 작업 폴더의 미커밋 변경은 보존하고 새 저장소의 작업용 worktree에서 진행했다.

## 사례 A. 고정된 감사인 기준을 독립 앱에 그대로 적용하는 문제

**문제 상황:** 원본 점검기는 특정 회계법인의 이름·고유번호·주소·대표자를 기준으로 삼고 있었다. 이를 범용 체험 앱에 그대로 쓰면 다른 감사인의 보고서를 넣어도 고정된 감사인과 다르다는 오류가 나올 수 있었다. 독립 화면으로 옮기는 것만으로는 해결되지 않는 기능상의 문제였다.

**AI 활용:** 사용자의 기존 코드 활용 요청을 구체화하는 과정에서 Codex가 의존성·공개용 화면·하드코딩된 점검 기준을 조사했다. 원본 코드 조사 역할과 독립 앱 구현 역할을 나누고, 감사인 기준은 화면에서 지정하도록 구현 지시를 세웠다.

**해결 과정:** 프로필을 이름·CIK·주소·대표자 네 값으로 나누어 사용자가 지정하게 했다. 기본값은 실제 회사의 값이 아닌 가상회계법인으로 구성했다. 사용자는 실제 파일을 점검할 때 해당 감사인의 기준으로 바꾼 뒤 실행한다. 내부 링크와 회사 로고도 공개용 구성에서 제외한다.

**최종 결과와 한계:** 프로필 입력을 기준으로 점검하는 흐름을 이번 과제용으로 구성했다. 입력값 자체의 최신성·정확성은 사용자가 확인해야 한다. 자동으로 모든 감사인의 공식 정보를 수집·검증하는 기능은 포함하지 않는다. 실제 실행 결과는 아래 검증 결과와 연결해 확인한다.

## 사례 B. 감사보고서와 검토보고서에 다른 규칙이 필요한 문제

**문제 상황:** 분·반기 검토보고서는 연차 감사보고서와 표현·구성·필수 확인 항목이 다르다. 모든 입력에 연차 55개 기준을 적용하면 맞는 문구까지 오류로 분류할 수 있다. 문서 코드를 모르는 파일에 임의로 규칙을 적용하는 것도 위험하다.

**AI 활용:** Codex에 현재 최신 코드의 서식 지원 범위를 확인하게 했다. 조사 결과 최신 원본에는 연차와 분·반기 검토보고서를 나누는 구현이 이미 있었다. 따라서 새로운 오류 수정을 했다고 기록하는 대신 그 구현을 보존하는 재사용 결정으로 남겼다.

**해결 과정:** `00760/00761`과 `90020/90220/90320/90420`를 구분하는 기존 규칙을 재사용한다. 범위 밖이거나 코드가 미확인인 문서는 점검을 중단하고 지원 범위를 안내한다. 검토보고서를 연차 55개 항목으로 일괄 채점하지 않는다.

**최종 결과와 한계:** 서식별 규칙 분리를 독립 앱에도 유지했다. 이 사례의 핵심 기여는 원본의 기존 보호 동작을 과제용 앱에 옮기는 과정에서 잃지 않도록 한 것이다. 서식·기준이 바뀌면 해당 규칙과 테스트를 함께 갱신해야 한다.

## 사례 C. 파일이 없는 방문자가 핵심 기능을 재현하기 어려운 문제

**문제 상황:** DSD는 일반적인 사용자에게 익숙하지 않은 업무 파일이다. 파일 선택 기능만 있으면 평가자가 앱을 열어도 점검 결과나 원문 근거를 직접 확인하기 어렵다. 실제 미공시 자료를 공개 체험용으로 올리는 방식도 적합하지 않다.

**AI 활용:** Codex가 가상 회사의 DSD를 브라우저에서 생성하고, 수정 전후를 같은 흐름으로 비교하는 체험 방식을 제안했다. 요구사항에는 실제 고객 자료를 포함하지 않으며 결과의 차이가 테스트로 확인되도록 명시했다.

**해결 과정:** 연차 오류 예시·수정 예시·검토보고서 예시를 합성 XML과 ZIP으로 만든다. 체험에서도 실제 파일과 같은 읽기·점검 경로를 사용한다. 사용자가 오류 예시를 실행한 뒤 수정 예시를 실행하면 어떤 구조적 문제가 달라지는지 살펴볼 수 있다.

**최종 결과와 한계:** 공개 방문자가 별도 자료를 준비하지 않고 핵심 기능을 실행하는 경로를 구성했다. 합성 샘플의 기대값 확인은 엔진 작동을 확인하는 시험이며 실제 모든 공시 문서에서 정확하다는 증거가 아니다. 실제 자료 대량 검증이나 오류율 측정은 수행한 범위만 별도로 보고한다.

## 사례 D. 자동 통과와 사람의 확인 완료가 섞이는 문제

**문제 상황:** 구조나 숫자 형식의 자동 점검이 끝나도 문장의 의미·보고서 범위·판단이 필요한 항목은 사람이 확인해야 한다. 화면이 완료율이나 통과 건수만 강조하면 남은 수동 확인을 놓칠 수 있다.

**AI 활용:** Codex에 기존 상태 체계와 수동 확인 부분을 보존하도록 요구했다. 기존 엔진의 `pass`, `fail`, `warn`, `manual`, `na`를 화면에 구분하고, 사람이 확인한 표시는 자동 판정과 별도로 저장하도록 정했다.

**해결 과정:** 오류·확인 필요·수동 확인·통과·해당 없음을 분리한다. 담당자가 확인 체크를 해도 기계의 원래 상태를 임의로 통과로 바꾸지 않는다. 내보낸 결과에도 이 구분이 드러나도록 한다.

**최종 결과와 한계:** 원본 엔진의 수동 판단 경계를 보존하는 설계로 구성했다. 이 사례 역시 원본에서 이미 존재한 상태 분리를 새 발명이나 전면 신규 수정으로 표현하지 않는다. 최종 업무 판단과 제출 책임은 실제 담당자의 확인을 거쳐야 한다.

## 사례 E. 원문 근거를 열면 닫기 버튼이 사라지는 화면 오류

**문제 상황:** Agent의 브라우저 시험에서 점검 결과의 근거 dialog를 열었을 때, 원문 블록을 찾기 위한 `scrollIntoView()`가 원문 패널뿐 아니라 상위 dialog까지 스크롤했다. 제목과 닫기 버튼이 화면 위로 사라져 사용자가 화면을 닫기 어려운 상태가 관측되었다. 코드를 읽기만 해서는 드러나지 않은 실제 화면 동작 문제였다.

**AI 활용:** Codex가 앱을 실행해 근거 화면을 열고, 제목·닫기 버튼의 위치를 확인했다. 이 문제를 브라우저 관측에 근거해 수정 대상으로 삼고, 원문을 찾는 동작이 바깥 dialog를 움직이지 않도록 수정하기로 했다.

**해결 과정:** `public/app.js`의 `highlightLocation()`에서 조상까지 영향을 주는 `scrollIntoView()` 호출 대신 `source-view`의 `scrollTop`만 조절했다. dialog를 열 때에는 `dialog.scrollTop = 0`으로 시작 위치를 고정했다. 원문에서 찾을 위치는 내부 패널 안에서 이동하고 바깥 제목과 닫기 버튼을 유지하도록 바꿨다.

**최종 결과와 한계:** 같은 근거 화면을 다시 실행한 브라우저 시험에서 닫기 버튼이 보이는 상태(`visible=true`)를 확인했다. 이는 Agent가 수행한 재현·수정·재실행 기록이며, 사용자가 직접 수행한 UAT로 표현하지 않는다. 모든 브라우저와 보조공학 환경의 동작까지 확인한 것은 아니다.

## 사례 F. 원문을 내려받을 때 Excel 수식으로 해석될 수 있는 경계 입력

**문제 상황:** 원문에서 가져온 글이 `=`, `+`, `-`, `@`로 시작하면 CSV를 Excel로 열 때 글이 아닌 수식으로 해석될 수 있다. 실제 공격이 발생한 사례가 아니라, 결과 내보내기 기능을 구현·시험하면서 확인한 경계 조건이다.

**AI 활용:** Codex가 다운로드 기능의 입력 경계를 검토하고 `=HYPERLINK(...)` 형태의 시험용 문자열을 fixture로 구성했다. 원문을 문자열로 보존하면서 수식 실행 대상으로 저장되지 않는지 확인하도록 테스트했다.

**해결 과정:** `public/export.js`에서 CSV 셀의 선행 공백 뒤에 수식 접두 문자가 있으면 작은따옴표를 붙인다. XLSX는 원문을 수식 셀이 아닌 `inlineStr` 문자열 셀로 기록한다. CSV의 보호 접두 문자와 XLSX의 문자열 셀 구조를 테스트로 확인한다.

**최종 결과와 한계:** 해당 경계 fixture가 포함된 Node 테스트 11개가 모두 통과했다. 브라우저에서 CSV와 XLSX 파일 다운로드도 성공했다. 다운로드 성공과 모든 Excel 버전에서의 동작 확인은 구분하며, 실제 공격이나 실제 사용자 피해가 발생했다고 주장하지 않는다.

### 사례 G. 비워진 것처럼 보이는 화면에 문서가 남는 문제

**문제 상황:** 독립 소스 리뷰가 '문서 비우기' 후 결과는 숨겨지지만 결과행·근거·헤더·파일 메타의 텍스트가 DOM에 남는 것을 발견했다. 상태 객체만 비우는 것으로는 '비우면 사라집니다'라는 안내를 충족하지 못했다.

**AI 활용:** 작성자와 별도 컨텍스트의 Codex 검토자에게 고정 커밋 6732e9d를 읽기 전용으로 검토하도록 맡겼다. 검토자가 실제 초기화 함수를 메모리 DOM 대역에서 실행해 잔존을 재현했고, 작성 Agent가 지적을 수용했다.

**해결 과정:** discardReport()로 상태·원문 객체·Blob URL뿐 아니라 결과행·근거·헤더·요약·제목의 문서별 DOM을 제거하도록 통합했다. 문서 비우기와 새 파일 점검 시작/실패에 같은 경로를 적용했다. 진행 중인 Excel 생성도 문서가 교체되면 다운로드하지 않는다.

**최종 결과와 한계:** 수정 전 소스에서 회귀 시험 2개가 실패하고 최종 소스에서 통과했다. 브라우저에서도 회사명 잔존 false, 근거·헤더·원문·파일 메타 텍스트 길이 0을 확인했다. 브라우저 메모리의 물리적 덮어쓰기를 보증하는 기능은 아니다.

### 사례 H. 좁은 화면에서 결과 표가 페이지를 밀어내는 문제

**문제 상황:** 모바일 폭의 결과 화면에서 문서 전체 폭이 582px로 늘어나 화면 폭 375px를 넘었다. 표 내부 스크롤만으로 제어될 것이라는 예상과 달랐다.

**AI 활용:** Codex가 실제 브라우저에서 반응형 폭을 적용해 첫 화면과 결과 화면의 document 폭을 비교했다. 처음 화면은 맞지만 결과 표가 생긴 뒤 넘치는 경로를 좁혔다.

**해결 과정:** grid 자식 main의 최소 폭을 0으로 지정하고 표 컨테이너의 최대 폭을 제한했다. 표의 최소 폭은 유지하되 표 내부에서만 가로 스크롤되게 했다.

**최종 결과와 한계:** 재시험에서 페이지 폭 375px와 문서 폭 375px가 같았다. 표는 내부 폭 334px에 내용 폭 540px로 가로 스크롤된다. 실제 모바일 기기 전체에서의 시험은 수행하지 않았다.

## 3. 검증과 남은 확인
