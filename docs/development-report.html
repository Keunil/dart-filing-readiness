1. 발견한 문제와 개발 목적

DART에 감사·검토보고서를 접수하기 전, R&Q 공시팀은 보고서의 구조와 기재 사항을 체크리스트에 따라 확인한다. 업무가 집중되는 시기에는 인턴을 포함한 여러 인력이 투입되어도 항목을 하나씩 수기로 확인하는 과정에서 병목이 발생하고 오류가 반복된다.

이 앱은 보고서에서 기계적으로 확인할 수 있는 항목을 먼저 점검한다. 담당자는 오류·확인 필요 항목과 원문 위치를 확인하고, 자동으로 판단할 수 없는 부분에 집중한다. 기존 인원 수나 오류율, 개발 전후 처리시간은 측정 자료가 없어 수치로 제시하지 않았다.

2. 주요 기능과 사용 순서

핵심 사용자는 접수 전 보고서의 구조를 확인하는 담당자다. 공개 방문자도 실제 업무 파일을 준비하지 않고 가상 회사의 DSD로 동일한 점검 흐름을 체험할 수 있게 했다.

주요 기능사용자가 확인할 수 있는 동작
DSD 선택·체험자신의 파일을 선택하거나 합성 샘플을 실행해 문서 정보를 확인한다.
감사인 기준 지정이름·CIK·주소·대표자를 설정한다. 기본 프로필은 가상 값이다.
서식별 점검연차 감사보고서와 분·반기 검토보고서의 규칙을 구분해 적용한다.
상태 구분·검색오류·확인 필요·수동 확인·통과·해당 없음을 구분하고 필요한 항목을 찾는다.
원문 근거 확인발견 사항의 헤더 정보와 문단·표 등 원문 위치를 확인한다.
확인 기록·내보내기사람이 검토한 표시를 자동 판정과 구분하고 결과를 내려받는다.

사용 순서

01 · 시작가상 체험을 실행하거나 DSD 파일을 선택한다.
02 · 기준 확인해당 감사인의 프로필과 문서 종류를 확인한다.
03 · 결과 검토상태별로 걸러 근거와 원문을 확인한다.
04 · 수동 확인사람의 판단이 필요한 항목을 검토한다.
05 · 비교 체험오류·수정 샘플을 실행해 결과 차이를 본다.
06 · 결과 보관필요한 결과를 사용자 기기에 내려받는다.

3. 앱 구조와 작동 원리

HTML·CSS·JavaScript를 제공하는 정적 웹 앱으로 구성했다. 별도 데이터베이스나 로그인, 외부 AI API 없이 파일 읽기부터 결과 생성까지 브라우저에서 수행한다.

구성역할
화면 · HTML/CSS파일 선택, 체험, 프로필 입력, 상태별 결과와 원문 근거를 배치한다.
동작 · JavaScript사용자 동작을 받아 읽기·점검을 실행하고 필터·확인 표시·다운로드를 처리한다.
DSD 읽기 모듈DSD는 ZIP 형식이다. 내부의 contents.xml·meta.xml에서 헤더·문단·표와 위치를 읽는다.
점검 엔진보고서 코드에 맞는 규칙을 실행하고 상태·발견 사항·원문 위치를 반환한다.
합성 체험 자료가상 회사의 XML을 브라우저에서 ZIP으로 만들어 실제 파일과 같은 경로로 처리한다.
정적 호스팅앱 소스 파일만 제공한다. 사용자가 고른 DSD를 업로드받는 API는 두지 않는다.

데이터 처리

처리 대상은 공시 전의 미공시 DSD일 수 있다. 원본 DSD와 분석 결과를 브라우저 메모리에 두고 서버로 보내거나 저장하지 않는다. 콘텐츠 보안 정책에 connect-src 'none'을 적용해 점검 중 네트워크 연결을 제한한다. 파일과 결과가 localStorage에 저장되는 구조로 설명하지 않는다.

사용자가 결과를 내려받으면 그 파일은 사용자 기기에 남는다. 웹 페이지 새로고침·닫기와 다운로드한 파일의 삭제는 서로 다른 동작이다.

재사용과 이번 과제의 변경

원본 기준 커밋은 0d4d1c6a2753c1c5e5499495dcd5fb67a152605e다. DSD 해석과 규칙 실행을 재사용해 기존 판정의 경계를 보존했다. 이번에는 독립 앱에 필요한 화면·프로필 설정·가상 샘플·내보내기·배포·제출 문서를 구성했다.

독립 공개본에는 업무 시스템의 사내 메뉴·내부 링크·회사 로고·실제 고객 자료를 넣지 않는다. 파일별 출처와 변경은 저장소의 docs/provenance.md에서 확인할 수 있다.

6. AI와 함께 문제를 해결한 과정

사용자는 실제 업무 문제·기존 코드 활용·과제 조건을 제공했다. Codex는 요구사항 추출, 최신 소스 조사, 구현·테스트·기록 역할을 나누어 수행했다. 아래 기록은 기존 기능의 재사용과 이번 개선을 구분한다.

A. 특정 감사인의 고정값을 적용하는 문제

문제 상황 원본의 특정 감사인 이름·CIK·주소·대표자 고정값을 독립 앱에 그대로 쓰면 다른 감사인의 보고서도 오류로 판정할 수 있었다.

AI 활용·해결 과정 Codex가 원본의 의존성과 고정 기준을 조사하고, 네 값을 사용자가 입력하는 프로필로 바꾸도록 구현 범위를 정했다. 기본값은 가상회계법인으로 제공한다.

최종 결과·한계 지정 프로필로 확인하는 흐름을 과제용으로 구성했다. 사용자가 입력한 기준의 최신성·정확성을 앱이 공식 인증하는 것은 아니다.

B. 검토보고서에 연차 기준을 적용하는 과탐

문제 상황 연차와 분·반기 문서에 같은 기준을 적용하면 올바른 검토보고서 표현도 오류가 될 수 있다.

AI 활용·해결 과정 최신 원본을 조사한 결과 서식별 분리 구현이 이미 있었다. 이를 재사용하고, 범위 밖·코드 미확인 입력을 임의로 점검하지 않게 구성한다.

최종 결과·한계 기존 보호 동작을 보존하는 재사용 결정이다. 이번 과제에서 새로 발견해 원본 규칙을 전면 수정했다고 쓰지 않는다.

C. 업무 파일이 없는 방문자의 재현 문제

문제 상황 파일 선택만 있으면 평가자가 DSD를 준비하지 못할 때 핵심 기능을 확인할 수 없다.

AI 활용·해결 과정 실제 고객 자료 대신 가상 회사 XML·ZIP을 브라우저에서 생성하는 체험을 구성했다. 수정 전후와 검토보고서를 같은 읽기·점검 경로로 처리한다.

최종 결과·한계 별도 자료 없이 실행할 수 있는 경로를 만들었다. 합성 자료의 기대값 일치는 실제 전체 문서의 정확도 검증과 구분한다.

D. 자동 통과와 수동 확인의 혼동

문제 상황 자동 점검이 끝나도 문장 의미·보고서 범위처럼 사람이 판단할 내용은 남는다.

AI 활용·해결 과정 기존 엔진의 다섯 상태를 화면에서 구분하고, 담당자의 확인 표시를 기계의 원래 상태와 따로 다루도록 요구했다.

최종 결과·한계 원본의 수동 판단 경계를 보존했다. 최종 업무 품질 승인은 실제 담당자의 확인이 필요하다.

위 네 사례는 구조·재사용 결정과 개선 사항이다. 실제 실행 중 발견·수정한 기능 오류와 경계 입력 시험은 다음 절에 따로 기록한다.

7. 실행 중 발견한 오류와 수정

아래 두 사례는 구현 후 실행·시험 과정에서 확인한 구체적인 문제다. AI가 앱을 실행하고 관측한 내용이며, 실제 사용자 UAT나 실제 보안 사고로 표현하지 않는다.

E. 근거 창을 열면 닫기 버튼이 사라짐

문제 상황 Agent가 브라우저에서 원문 근거 dialog를 열자, 블록 위치를 찾는 scrollIntoView()가 원문 패널의 조상인 dialog까지 스크롤했다. 제목과 닫기 버튼이 화면 위로 밀려나 보이지 않았다.

AI 활용 Codex는 실제 화면에서 제목·닫기 버튼 위치를 확인해 재현했다. 원문 위치로 이동하는 동작을 내부 패널에만 적용하도록 수정 방향을 정했다.

해결 과정 public/app.js의 highlightLocation()에서 source-view.scrollTop만 조절하도록 바꾸었다. dialog를 열 때는 dialog.scrollTop = 0으로 초기 위치를 고정했다.

최종 결과 같은 화면을 다시 실행한 시험에서 닫기 버튼 노출(visible=true)을 확인했다. 원문은 내부에서 이동하고 바깥 제목·닫기 조작은 유지되었다. 모든 브라우저에서의 동작까지 시험한 것은 아니다.

실제 수정 순서
AI의 브라우저 실행 → 근거 창의 조상 스크롤 관측 → 내부 패널만 스크롤하도록 수정 → 재실행하여 닫기 버튼 노출 확인

F. 원문이 Excel 수식으로 해석될 수 있는 입력

문제 상황 원문을 CSV로 내보낼 때 글이 =·+·-·@로 시작하면 Excel에서 수식으로 해석될 수 있다. 실제 공격 사례가 아니라 내보내기 경계 입력을 시험하며 확인한 조건이다.

AI 활용 Codex가 =HYPERLINK(...) 형태의 문자열을 fixture로 구성해 결과 파일이 수식 대신 문자열로 처리되도록 확인하는 시험을 만들었다.

해결 과정 CSV는 선행 공백 뒤의 수식 접두 문자를 검사해 작은따옴표를 붙인다. XLSX는 inlineStr 문자열 셀로 기록한다. 코드와 테스트에서 보호 접두 문자 및 문자열 셀 구조를 확인한다.

최종 결과 경계 입력 fixture를 포함한 Node 테스트가 통과했고 브라우저에서 CSV·XLSX 다운로드도 성공했다. 모든 Excel 버전의 실제 열기 동작을 확인한 것은 아니며 실제 피해가 있었다고 주장하지 않는다.

G. 비워진 화면에 남은 문서 텍스트

문제 상황 독립 리뷰에서 ‘문서 비우기’가 결과를 가리기만 하고 결과행·근거·헤더·파일 메타의 텍스트와 이벤트를 남기는 것을 발견했다. 메모리에서만 처리한다는 설명을 지키려면 숨김과 제거를 구별해야 했다.

AI 활용 작성자와 별도 컨텍스트의 Codex에게 고정 커밋을 읽기 전용으로 검토하도록 맡겼다. 검토자가 실제 초기화 함수를 메모리 DOM 대역에서 실행해 잔존을 재현했고, 작성 Agent가 수용했다.

해결 과정 공용 초기화 함수에서 상태·원문 뷰·Blob URL과 문서별 DOM을 함께 제거했다. 문서 비우기뿐 아니라 새 파일을 읽기 시작하거나 실패하는 경우에도 같은 경로를 사용한다.

최종 결과 수정 전 소스에서 회귀 시험 2개가 실패하고 수정본에서 통과했다. 브라우저에서도 회사명 잔존 false, 근거·헤더·원문·메타 텍스트 길이 0을 확인했다. 브라우저 메모리의 물리적 덮어쓰기를 보증하는 기능은 아니다.

H. 모바일 결과 표의 가로 넘침

문제 상황 좁은 화면에서 결과가 나타나자 문서 폭이 582px로 늘어나 실제 내용 영역 375px를 넘었다. 첫 화면만 봐서는 찾지 못한 문제였다.

AI 활용 Codex가 브라우저의 반응형 폭을 적용해 결과 생성 전후의 페이지 폭을 비교했다. 표의 최소 폭이 grid 자식을 밀어내는 경로를 좁혔다.

해결 과정 main의 최소 폭을 0으로, 표 컨테이너의 최대 폭을 100%로 제한했다. 표의 열은 보존하고 표 안에서만 가로 스크롤하게 했다.

최종 결과 재시험에서 페이지 폭과 문서 폭이 모두 375px로 같았다. 표 내부 334px에 내용 540px만 스크롤된다. 실제 모바일 기기 전체를 시험한 것은 아니다.
